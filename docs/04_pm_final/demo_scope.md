# デモフェーズ：スコープ定義

## 1. プロジェクト概要

**プロジェクト名**：SuperApp デモフェーズ
**プロジェクトID**：SA-DEMO-2025
**バージョン**：1.0
**日付**：2025-06-01
**ステータス**：ドラフト

SuperAppは、Django REST APIゲートウェイ（App1）とPHP/Apacheストレージサービス（App2）からなる2マイクロサービスアプリケーションです。本スコープ定義文書は、デモフェーズにおける納品物、境界線、仮定条件、除外事項を明確に定義します。

---

## 2. デモスコープステートメント

### 2.1 目的

SuperAppのコア機能——ユーザー認証、ファイルアップロード検証、クロスサービスファイルトランスポート、7zアーカイブ解凍——をエンドツーエンドで実証し、ステークホルダーに対してシステムアーキテクチャと技術設計の妥当性を示す。

### 2.2 境界線

#### 2.2.1 インクルード（スコープ内）

**App1 — ゲートウェイサービス（Django/uWSGI）**

| 機能 | エンドポイント | 説明 |
|------|---------------|------|
| ユーザー登録 | POST /gateway/user/ | 新しいユーザーアカウントの作成 |
| トークン取得 | POST /auth/token/ | JWTアクセストークンの発行 |
| トークンリフレッシュ | POST /auth/refresh-token/ | JWTトークンの更新 |
| ファイルアップロード | POST /gateway/transport/ | ZIPファイル検証とApp2への転送 |
| ユーザー検索 | POST /gateway/user/find/ | 条件ベースのユーザー検索（ページネーション付き） |
| ヘルスチェック | GET /gateway/health/ | App2モジュールの死活監視 |

**App2 — ストレージサービス（PHP/Apache）**

| 機能 | エンドポイント | 説明 |
|------|---------------|------|
| ファイル受領・解凍 | POST /storage.php | ZIPファイル受領、7z解凍、ストレージ配置 |
| ヘルスチェック | GET /health.php | サービス死活確認 |

**インフラストラクチャ**

| 項目 | 詳細 |
|------|------|
| コンテナ编排 | Docker Compose（docker-compose.yaml） |
| ネットワーク | Docker内部ネットワーク（app1↔app2） |
| ポート公開 | App1: 8000 |
| データ永続化 | App2: flag.txtボリュームマウント |

#### 2.2.2 エクスクルード（スコープ外）

| 項目 | 理由 |
|------|------|
| フロントエンドUI | APIレベルでのデモに限定 |
| 本番デプロイメント | デモはローカルコンテナ環境のみ |
| パフォーマンステスト | 機能検証が主目的 |
| セキュリティペネトレーションテスト | CTFコンテキストを踏まえた設計理解は行うが、正式な脆弱性評価は対象外 |
| データベース変更（SQLite→他） | 既存設計の維持 |
| モニタリング/ロギングインフラ | デモ規模では不要 |
| CI/CDパイプライン | 後工程で検討 |

## 3. デモフロー

### 3.1 ユーザージャーニー

```
┌─────────────┐
│  ステップ1   │ 環境起動
│ docker compose up
└──────┬──────┘
       │
┌──────▼──────┐
│  ステップ2   │ ヘルスチェック
│ GET /gateway/health/?module=/health.php
│ 期待: {"data": "OK"}
└──────┬──────┘
       │
┌──────▼──────┐
│  ステップ3   │ ユーザー登録
│ POST /gateway/user/
│ Body: {username, email, password}
│ 期待: username文字列
└──────┬──────┘
       │
┌──────▼──────┐
│  ステップ4   │ トークン取得
│ POST /auth/token/
│ Body: {username, password}
│ 期待: {access, refresh}
└──────┬──────┘
       │
┌──────▼──────┐
│  ステップ5   │ ファイルアップロード
│ POST /gateway/transport/
│ Headers: Authorization: Bearer <token>
│ Files: file=@sample.zip
│ 期待: "OK"
└──────┬──────┘
       │
┌──────▼──────┐
│  ステップ6   │ ストレージ確認
│ App2のstorage/<user-id>/ディレクトリ
│ 解凍済みファイルの存在確認
└──────┬──────┘
       │
┌──────▼──────┐
│  ステップ7   │ ユーザー検索
│ POST /gateway/user/find/?offset=0
│ Headers: Authorization: Bearer <token>
│ Body: {username: "xxx"}
│ 期待: ユーザーリスト
└──────┬──────┘
       │
┌──────▼──────┐
│  ステップ8   │ 環境停止
│ docker compose down
└─────────────┘
```

### 3.2 ワウモーメント

| No. | モーメント | 説明 | 期待される反応 |
|-----|-----------|------|---------------|
| 1 | ワンコマンド起動 | `docker compose up` で全サービス即時稼働 | 「シンプルで良い」 |
| 2 | エンドツーエンドファイルフロー | アップロードから解凍まで自動処理 | 2サービス連携のスムーズさ |
| 3 | 認証ガード付きAPI | JWTトークンなしではアクセス不可 | セキュリティ設計の意識 |
| 4 | ファイル検証 | 許可拡張子のみ受け付けるバリデーション | セキュリティフィルタリング |
| 5 | ダイナミックスケーリング | uWSGIのcheaperモードによる自動プロセス調整 | 運用効率への配慮 |

## 5. 仮定条件

| ID | 仮定条件 | 影響度 | 検証方法 |
|----|---------|--------|---------|
| A1 | DockerおよびDocker Composeが実行環境にインストール済み | 高 | デモ前確認 |
| localhost:8000 が利用可能 | 高 | ポート競合チェック |
| A3 | テスト用ZIPファイルは許可拡張子のみを含む | 中 | ファイル検証テスト |
| A4 | ローカルネットワークの安定性 | 高 | 事前接続テスト |
| A5 | SQLite3でデモ規模データ処理が可能 | 低 | 負荷テスト（簡易） |
| A6 | ステークホルダーはデモ日に参加可能 | 高 | 日程調整メール |

---

## 6. 制約条件

| ID | 制約 | 説明 |
|----|------|------|
| C1 | コード変更不可 | 既存コードベースをデモ用に修正しない |
| C2 | データベース固定 | SQLite3の使用を維持 |
| C3 | APIレベルデモ | フロントエンドUIは提供しない |
| C4 | ローカル環境 | 外部デプロイメントは行わない |
| C5 | タイムリミット | デモ実施は60分以内 |
